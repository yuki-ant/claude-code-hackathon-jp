# Claude Code ハッカソン

## このハッカソンについて

このハッカソンでは、チームごとにシナリオを1つ選び、Claude Code を使って課題に取り組みます。シナリオはいずれも、エンタープライズの現場でよくある悩みを1日で挑める形に凝縮したものです。中身を把握している人が誰もいないモノリス、方針がなかなか固まらないクラウド移行、システムごとに「顧客」の定義が食い違っている会社。心当たりのある話ばかりではないでしょうか。

進め方は自由です。各シナリオにはチャレンジをいくつか用意していますが、どの順番で取り組むか、どんな技術スタックを使うか、どこまで作り込むか(あるいは何を独自に足すか)はチームに委ねます。審査で重視するのは、チェックリストをいくつ消化したかではなく、どれだけ大胆に挑み、どれだけ的確に判断できたかです。

---

## 進め方

シナリオを1つ選んだら、あとはチームで手を動かして、時間の許す限り進めてください。

チャレンジは、時間内にはすべて終わらない分量をあえて用意しています。広く浅くこなすより、面白いと思ったものに絞って深く掘るほうが評価につながります。手分けできる作業は並行して進め、チーム内の調整には Claude も活用してください。

---

## チームでの動き方

シナリオは SDLC の全工程をカバーしているため、PM、アーキテクト、開発、テスト、プラットフォームのどの観点にも取り組みがいのある仕事があります。とはいえ、すべての役割が揃ったチームはまずないはずです。揃っていなくても問題ありません。普段の職種にとらわれず、必要な役割は全員で分担してください。ふだん関わらない領域で Claude Code がどこまで戦力になるかを試せるのも、このハッカソンの醍醐味のひとつです。

チャレンジの分担は早めに決めましょう。`CLAUDE.md` をチームで共有して育てていけば、メンバー全員が同じ規約を Claude に教えられます。また、コミットはこまめに行ってください。コミット履歴も提出物の一部であり、審査ではそこから開発の過程を読み取ります。

---

## ルール

1. **技術スタックは自由です。** ただしシナリオ5のみ、**Claude Agent SDK** の使用が必須です。初めて使う場合も、他のフレームワークから移行する場合も、Claude に手伝ってもらいながらで構いません。
2. **スターターコードやデータ、ドキュメントは自分たちで用意することがあります。** シナリオに「稼働12年のモノリスがある」と書いてあれば、そのモノリスを生成するところから始めてください。それも仕事のうちです。任意で使えるスターターリポジトリを用意したシナリオもあります。
3. **役割は全員で分担します。** PM、アーキテクト、開発、テスター、データエンジニア、インフラエンジニア。この顔ぶれが揃っていなくても、チームとしてすべての役割をこなすことになります。
4. **コミット履歴も審査対象です。** 完成品だけでなく、そこに至る過程も見せてください。
5. **`CLAUDE.md` を活用しましょう。** チームの規約は早めに教え込むほど効いてきます。
6. **成果は必ずドキュメントにまとめます。** 何を作り、次に何をする予定だったのかが分かる `README.md`(テンプレートは後述)をリポジトリに含めてください。
7. **プレゼン資料も作成します。** 審査を通過した場合にそのまま発表できる水準の HTML プレゼンを Claude Code で作成し、発表の有無にかかわらずリポジトリに含めてください。日本語フォントには Noto Sans JP を使用します(Anthropic Sans は日本語グリフ非対応のため)。
8. **審査は Claude が行います。** 提出物をまず Claude が評価し、上位の数チームが実際に発表します。

## 活用したいテクニック

以下は、Claude Code Architecture 認定試験で問われるパターンの一覧です。使用が必須のシナリオはありませんし、どのチャレンジでどれを使うかの指定もありません。それでも掲載しているのは、ハッカソンを認定試験対策の実践の場としても使いたい、というチームが多いためです。磨きたいパターンを2〜3個選び、取り組むチャレンジの中で試してみてください。

**エージェントアーキテクチャ**

- Task tool を使った、コーディネーター+専門サブエージェントの構成。コンテキストは呼び出しのたびに*明示的に*渡すこと(Task サブエージェントはコーディネーターのコンテキストを引き継ぎません)。
- 停止条件は本物のシグナルで判定する。「テキストをパースして判断」や「イテレーション回数の上限」で済ませない。
- `fork_session` で同じ入力に2通りのアプローチをぶつけて比較する。

**ツール設計と MCP**

- ツールの説明文には、そのツールが*何をするか*だけでなく*何をしないか*も書く。入力フォーマット、エッジケース、クエリ例も添える。
- 構造化したエラーレスポンス(`isError: true` に理由コードと対処のヒントを添える)を返し、エージェントが自力でリカバリーできるようにする。
- 専門エージェント1体あたりのツール数は絞る。数個を超えたあたりから、ツール選択の精度は落ちていきます。
- 作ったシステムには MCP サーバーを被せて、まっさらな Claude セッションでも一発で正しいツールを選べるようにする。

**Claude Code の設定**

- `CLAUDE.md` の3階層構成。ユーザーレベルには個人の好み、プロジェクトレベルには VCS で共有するチーム規約、ディレクトリレベルにはモジュール固有の事情を。
- カスタムスラッシュコマンドとスキルは役割を分けて使う。コマンドは決まった手順の実行、スキルは再利用できるノウハウの置き場です。
- 失敗すると取り返しのつかない操作には Plan Mode、安全な操作は直接実行。そう分けた理由を説明できるようにしておく。
- CI では非対話モードの Claude Code を使う。ツールのスコープは絞り、本番パスへの書き込み権限は渡さない。

**プロンプトエンジニアリング**

- 曖昧な修飾語は明示的な基準に置き換える。「重要な」「大幅な」「最近の」という言葉が出てきたら、そこはしきい値を決めるべきサインです。
- few-shot の例にはネガティブケースと境界ケースを混ぜる。切れ味のいい例2つは、ぼんやりした例8つに勝ります。
- パースが必要な出力には JSON Schema 付きの `tool_use` を使う。「JSON で出力してください」とお願いしない。
- 検証リトライループを組む。バリデーターが出力をチェックし、エラー内容をフィードバックして、Claude に最大 N 回やり直させる。リトライ回数とエラー種別はログに残します。

**コンテキスト管理**

- 決定論的に守りたいルールはフックで(ブロックは `PreToolUse`、マスキングは `PostToolUse`)、確率的な好みはプロンプトで伝える。どちらをどちらにしたのか、理由を ADR に残しておく価値があります。この使い分けは試験でも繰り返し問われます。
- エスカレーションルールは「エージェントが自信を持てないとき」ではなく、カテゴリ+確信度+影響度の組み合わせで定義する。
- 人間によるレビューには、層化サンプリングとフィールド単位の確信度を組み合わせる。

## 審査

一次審査は Claude が行い、上位チームが実際に発表します。

次の3ファイルは必ず読まれます。

1. `README.md`
2. `presentation.html`
3. `CLAUDE.md`

この3つが実質的なプレゼン資料です。作成を後回しにしないでください。仮に Claude がこの3ファイルしか読まなかったとしても、何を作ったのか、なぜそれに価値があるのか、どこまで到達したのか、そして Claude Code に自分たちのやり方をどう教えたのかが伝わるように仕上げましょう。リポジトリの中身をどこまで深く読むかは分かりません。この3つで評価が決まると考えておくのが安全です。

**評価の観点**(最終的な表彰カテゴリは当日発表しますが、方向性は次のとおりです):

- **本番投入にいちばん近い。** 月曜日にそのまま運用チームへ引き渡せる完成度。
- **アーキテクチャ思考が光る。** ADR、図、そして後から誰かに感謝されるような意思決定。
- **テストがうまい。** カバレッジの数字ではなく、意地悪な発想、エッジケース、eval。
- **プロダクトワークが丁寧。** ちゃんと物語として読めるユーザーストーリー。読み手を説得できるドキュメント。
- **Claude Code の使い方が独創的。** サブエージェント、フック、スキル。運営の予想を裏切る何か。
- **ワイルドカード:** ベスト CI/CD、ベスト・レガシー考古学、ベスト「失敗したらどうなる」思考、品質を保ったまま最も遠くまで到達したチーム、シナリオの要件そのものに疑問を投げかけて*実際に正しかった*チーム。

## 提出

提出に必要なのは次の3ファイルです。

1. **`README.md`**:チームの成果をまとめたもの。下のテンプレートを使ってください。
2. **`CLAUDE.md`**:Claude Code に自分たちのやり方をどう教えたのかが分かるもの。
3. **`presentation.html`**:Claude Code で作った HTML プレゼン。指名されたらすぐ発表できる状態にしておきます。日本語フォントには Noto Sans JP を使用してください(Anthropic Sans は日本語グリフ非対応のため)。

**推奨:** 3ファイルを、テーブル名とチーム名を付けたフォルダ(例: `Table1_SonnetSlayers/`)に入れて、当日案内するリンクへフォルダごとアップロードしてください。

**代替手段:** フォルダのままアップロードできない場合は、同じ命名規則で zip にまとめて(例: `Table1_SonnetSlayers.zip`)アップロードしてください。

どちらの場合も、**提出はチームにつき1回**です。

**顧客データ・社内データの持ち込みは厳禁です。** 提出物は、外部に公開しても差し支えない内容だけで構成してください。
