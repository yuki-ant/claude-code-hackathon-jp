# Claude Code ハッカソン

## このハッカソンについて

これはハッカソンです。皆さんにはチームとシナリオ、そして Claude Code が与えられます。シナリオはどれも、エンタープライズの現場でよくある難題を1日サイズに凝縮したものです。中身を把握している人が誰もいないモノリス。方針がいつまでも固まらないクラウド移行。システムが7つもあるのに「顧客」の定義がひとつも一致しない会社。どこかで見たような話ばかりのはずです。

進め方に決まりはありません。各シナリオには取り組みがいのあるチャレンジをいくつか挙げていますが、どの順番で、どんな技術スタックで、どこまでやるか(あるいは何を上乗せするか)はチームの自由です。審査で見たいのはチェックリストを埋めた数ではなく、どれだけ大胆に挑んで、どれだけ的確に判断したかです。

---

## 進め方

シナリオを1つ選んだら、あとはチームで行けるところまで進むだけです。

チャレンジは、時間内にはこなしきれない量をあえて用意しています。大事なのは、広く浅くではなく**狭く深く**。面白そうなものを選んで、手分けできる作業は並行して進めましょう。チーム内の交通整理は Claude に任せるのも手です。

---

## チームでの動き方

シナリオは SDLC の全工程にまたがっているので、PM、アーキテクト、開発、テスト、プラットフォームのどの立場にも、ちゃんとやるべき仕事があります。とはいえ、全役割の担当者が揃ったチームはまずないでしょう。それで構いません。**普段の職種は忘れて、全員がすべての役割を演じてください。** Claude Code は肩書きなど気にしませんし、普段は手を出さない領域でこのツールがどこまで戦力になるかを確かめられるのは、このハッカソンならではの楽しみです。

チャレンジの分担は早めに決めましょう。`CLAUDE.md` をチームで共有しながら育てれば、全員が同じ規約をツールに教え込めます。コミットはこまめに。コミット履歴も提出物の一部で、審査員はそこから開発の道のりを読み取ります。

---

## ルール

1. **技術スタックは自由です。** 唯一の例外として、シナリオ5だけは **Claude Agent SDK** が必須です。初めてでも、他のフレームワークからの乗り換えでも、習得は Claude に手伝ってもらいましょう。
2. **スターターコードやデータ、ドキュメントは自作になることがあります。** シナリオに「築12年のモノリスがある」と書いてあったら、そのモノリスを生成するところから仕事です。任意で使えるスターターリポジトリを用意したシナリオもあります。使うかどうかはお任せします。
3. **役割はすべて演じます。** PM、アーキテクト、開発、テスター、データエンジニア、インフラエンジニア。そういうメンバー構成で来ていなくても、チームとして全部こなすことになります。
4. **コミット履歴も審査対象です。** 完成品だけでなく、そこへたどり着くまでの過程を見せてください。
5. **`CLAUDE.md` を味方につけましょう。** チームの規約は早いうちに教え込むほど効いてきます。
6. **成果は必ずドキュメントに。** 何を作り、次に何をやるつもりだったのかが分かる `README.md`(テンプレートは後述)をリポジトリに入れてください。
7. **プレゼンも作ります。** 審査を勝ち抜いたらそのまま登壇できる水準の HTML プレゼンを Claude Code で作り、発表するかどうかにかかわらずリポジトリに含めてください。日本語フォントは Noto Sans JP を使います(Anthropic Sans は日本語グリフ非対応のため)。
8. **審査するのは Claude です。** 提出物はまず Claude が評価し、上位の数チームがライブで発表します。

## 活用したいテクニック

ここに挙げるのは、Claude Code Architecture 認定試験の出題範囲になっているパターンです。使わなければいけないシナリオはありませんし、どのチャレンジでどれを使うべきという指定もありません。それでも載せているのは、せっかくならハッカソンを認定試験の練習台にもしたい、というチームが多いからです。腕を磨きたいパターンを2〜3個選んで、取り組むチャレンジの中で試してみてください。

**エージェントアーキテクチャ**

- Task tool を使った、コーディネーター+専門サブエージェントの構成。コンテキストは呼び出しのたびに*明示的に*渡すこと(Task サブエージェントはコーディネーターのコンテキストを引き継ぎません)。
- 停止条件は本物のシグナルで判定する。「テキストをパースして判断」や「イテレーション回数の上限」で済ませない。
- `fork_session` で同じ入力に2通りのアプローチをぶつけて比較する。

**ツール設計と MCP**

- ツールの説明文には、そのツールが*何をするか*だけでなく*何をしないか*も書く。入力フォーマット、エッジケース、クエリ例も添える。
- 構造化したエラーレスポンス(`isError: true` に理由コードと対処のヒントを添える)を返し、エージェントが自力でリカバリーできるようにする。
- 専門エージェント1体あたりのツール数は絞る。数個を超えたあたりから、ツール選択の精度は落ちていきます。
- 作ったシステムには MCP サーバーを被せて、まっさらな Claude セッションでも一発で正しいツールを選べるようにする。

**Claude Code の設定**

- `CLAUDE.md` の3階層構成。ユーザーレベルには個人の好み、プロジェクトレベルには VCS で共有するチーム規約、ディレクトリレベルにはモジュール固有の事情を。
- カスタムスラッシュコマンドとスキルは役割を分けて使う。コマンドは決まった手順の実行、スキルは再利用できるノウハウの置き場です。
- 失敗すると取り返しのつかない操作には Plan Mode、安全な操作は直接実行。そう分けた理由を説明できるようにしておく。
- CI では非対話モードの Claude Code を使う。ツールのスコープは絞り、本番パスへの書き込み権限は渡さない。

**プロンプトエンジニアリング**

- 曖昧な修飾語は明示的な基準に置き換える。「重要な」「大幅な」「最近の」という言葉が出てきたら、そこはしきい値を決めるべきサインです。
- few-shot の例にはネガティブケースと境界ケースを混ぜる。切れ味のいい例2つは、ぼんやりした例8つに勝ります。
- パースが必要な出力には JSON Schema 付きの `tool_use` を使う。「JSON で出力してください」とお願いしない。
- 検証リトライループを組む。バリデーターが出力をチェックし、エラー内容をフィードバックして、Claude に最大 N 回やり直させる。リトライ回数とエラー種別はログに残します。

**コンテキスト管理**

- 決定論的に守りたいルールはフックで(ブロックは `PreToolUse`、マスキングは `PostToolUse`)、確率的な好みはプロンプトで伝える。どちらをどちらにしたのか、理由を ADR に残しておく価値があります。この使い分けは試験でも繰り返し問われます。
- エスカレーションルールは「エージェントが自信を持てないとき」ではなく、カテゴリ+確信度+影響度の組み合わせで定義する。
- 人間によるレビューには、層化サンプリングとフィールド単位の確信度を組み合わせる。

## 審査

一次審査は Claude が行い、上位チームがライブで発表します。

**確実に読まれるのは、次の3つです。**

1. `README.md`
2. `presentation.html`
3. `CLAUDE.md`

この3つが皆さんのピッチそのものです。後回しにしないでください。極端な話、Claude がこの3ファイルしか読まなかったとしても、何を作ったのか、なぜそれに価値があるのか、どこまで到達したのか、そして自分たちの流儀をツールにどう教えたのかが伝わる状態にしておくこと。リポジトリの奥まで読まれるかどうかは分かりません。この3つで勝負が決まると思ってください。

**評価の観点**(最終的な表彰カテゴリは当日のお楽しみですが、方向性は次のとおりです):

- **本番投入にいちばん近い。** 月曜日にそのまま運用チームへ引き渡せる完成度。
- **アーキテクチャ思考が光る。** ADR、図、そして後から誰かに感謝されるような意思決定。
- **テストがうまい。** カバレッジの数字ではなく、意地悪な発想、エッジケース、eval。
- **プロダクトワークが丁寧。** ちゃんと物語として読めるユーザーストーリー。読み手を説得できるドキュメント。
- **Claude Code の使い方が独創的。** サブエージェント、フック、スキル。私たちの予想を裏切る何か。
- **ワイルドカード:** ベスト CI/CD、ベスト・レガシー考古学、ベスト「失敗したらどうなる」思考、品質を保ったまま最も遠くまで到達したチーム、シナリオの要件そのものに疑問を投げかけて*実際に正しかった*チーム。

## 提出

必要なのは次の3ファイルです。

1. **`README.md`**:皆さんの物語を語るもの。下のテンプレートを使ってください。
2. **`CLAUDE.md`**:Claude Code に自分たちのやり方をどう教えたのかが分かるもの。
3. **`presentation.html`**:Claude Code で作った HTML プレゼン。指名されたらすぐ発表できる状態にしておきます。日本語フォントは Noto Sans JP を使ってください(Anthropic Sans は日本語グリフ非対応のため)。

**推奨:** 3ファイルを、テーブル名とチーム名を冠したフォルダ(例: `Table1_SonnetSlayers/`)に入れて、当日案内するリンクへフォルダごとアップロードしてください。

**代替手段:** フォルダのままアップロードできない場合は、同じ命名規則で zip にまとめて(例: `Table1_SonnetSlayers.zip`)アップロードしてください。

どちらの場合も、**提出はチームにつき1回**です。

**顧客データ・社内データの持ち込みは厳禁。** 提出物は、外部に見せても差し支えない内容だけで構成してください。

| # | チャレンジ | ステータス | 備考 |
|---|---|---|---|

いちばん大きな判断と、その理由。詳細な ADR は `/decisions` へのリンクで。
